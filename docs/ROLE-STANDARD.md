# Role 100% standard (v2 - executable engines)

A role is NOT a job description. A role is a WORKER: an executable core
that produces a correct deliverable standalone, gate-checks its own
output, and goes deeper when the Aero Agent Skills library is present.

## Required anatomy (every role, no exceptions)

```
roles/<role-slug>/
├── ROLE.md          # contract: identity, deliverable, workflow, gates,
│                    #   boundaries, HOW TO RUN (cli.py)
├── SOURCES.md       # standards referenced (summary-not-copy)
├── templates/       # ONE filled deliverable: the generated worked
│                    #   example for the reference item (ZERO blank ___)
├── core/
│   └── <role>_core.py   # EXECUTABLE DOMAIN ENGINE (the worker)
│                        #   - domain tables (real rules, not invented)
│                        #   - computations that produce REAL numbers
│                        #   - build_<deliverable>() -> content model
│                        #   - render_<deliverable>_markdown() -> doc
│                        #   - check_<deliverable>() evidence gates
│                        #   - example_item() for tests/demo
├── cli.py           # run the role:
│                    #   build (project facts -> filled deliverable)
│                    #   check (deliverable -> gate PASS/FAIL)
├── tests/
│   ├── test_<role>_core.py   # domain rules + builder + gates + STANDALONE
│   └── test_role_<slug>.py   # bound-skill resolution + structure
```

## 100% requirements (the founder's bar)

1. **Templates are FILLED deliverables.** Zero `___` blanks. The template
   IS a correct, complete example output generated by the core for the
   reference item - showing exactly what a correct deliverable looks like.
2. **Core does the job standalone.** `AEROSKILLS_DEV=/nonexistent` +
   `python3 cli.py build` produces a correct deliverable. No library.
3. **Evidence gates are executable.** `check_*` in core verifies the
   deliverable meets the role's gates: level/severity identified, numbers
   present, structure complete, sign-off honest (draft, never approval).
4. **Boundary is code-enforced.** The rendered deliverable always carries
   the DRAFT + human-review + not-an-approval marker.
5. **With-skills integration.** The role binds real leaves (verified in
   role test); core does not depend on them but the workflow names the
   skills that deepen each stage.
6. **Tests prove all of it.** Core tests cover domain rules, builder
   correctness, gate pass/fail, and standalone mode.

## Domain-logic rule

Every number the core produces must come from a REAL domain rule in the
bound AeroSkills leaves (which encode FAR/CS/standards practice) or from
the public standards themselves (FAR/CS quotable). NEVER invent an
allowable, a factor, or a rule. When unsure, encode the conservative
default and cite the source in SOURCES.md.

## CLI contract

```
python3 cli.py build [--out file.md] [--<fact> value...]   # produce deliverable
python3 cli.py check --file file.md [--level X]            # gate-check
```

## Gate-check vocabulary (render markers that MUST exist)
- The deliverable title (e.g. "Plan for Software Aspects of Certification")
- The level/DAL/severity when applicable
- The key computed numbers (coverage target, budget, margin)
- "draft" and "not an approval" markers
